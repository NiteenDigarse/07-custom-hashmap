# CustomHashMap — C++ Data Structure Project

A custom implementation of a hash map in modern C++, built from scratch to understand hash tables, collision handling, dynamic memory management, rehashing, and object ownership.

The project implements a key-value data structure inspired by `std::unordered_map`, using an array of buckets and separate chaining with linked lists.

## Overview

A hash map stores data as key-value pairs and uses a hash function to determine where each key should be stored.

For example:

```cpp
CustomHashMap<int, std::string> users;

users.insert(1, "Alice");
users.insert(2, "Bob");

std::cout << *users.find(1) << '\n';
```

Output:

```text
Alice
```

Unlike a simple array, a hash map uses hashing to locate entries efficiently. Multiple keys can map to the same bucket, so the implementation must handle collisions correctly.

This project implements the core mechanisms behind a hash map instead of relying entirely on the standard library container.

## How It Works

### 1. Entry Structure

Each entry stores a key, its associated value, and a pointer to the next entry in the same bucket.

```cpp
struct Entry
{
    Key key;
    Value value;
    Entry* next = nullptr;
};
```

The `next` pointer links entries that belong to the same bucket.

### 2. Bucket Array

The map maintains an array of pointers to entries.

```cpp
Entry** buckets_ = nullptr;
```

Each element of this array represents the head of a linked list.

The initial bucket count is eight.

```cpp
std::size_t bucket_count_ = 8;
```

The bucket array is dynamically allocated and initialized with null pointers.

### 3. Hash Function

The hash function converts a key into a hash value.

```cpp
std::size_t hash_key(const Key& key) const
{
    return hash_(key);
}
```

The default hashing policy uses `std::hash<Key>`.

### 4. Bucket Index

The hash value is reduced to a valid bucket index using the modulo operator.

```cpp
std::size_t bucket_index(
    const Key& key,
    std::size_t count) const
{
    return hash_key(key) % count;
}
```

For example, if a hash value is `27` and the bucket count is `8`:

```text
bucket_index = 27 % 8
bucket_index = 3
```

The key is assigned to bucket index `3`.

## Collision Handling

A collision occurs when different keys map to the same bucket.

This implementation uses **separate chaining**, where each bucket contains a linked list of entries.

Example:

```text
Bucket 0: nullptr

Bucket 1: [Key 11 | Value 110] -> nullptr

Bucket 2: [Key 18 | Value 180] -> [Key 10 | Value 100] -> nullptr

Bucket 3: nullptr
```

The example illustrates two entries sharing bucket `2`.

When inserting an entry:

1. Calculate the bucket index.
2. Traverse the bucket's linked list.
3. Check whether the key already exists.
4. Reject duplicate keys.
5. Otherwise, insert a new entry at the beginning of the list.

Inserting at the beginning takes constant time after the duplicate-key search has completed.

When deleting an entry, the implementation handles three cases:

- Deleting the head node.
- Deleting a middle node.
- Deleting the last node.

The links are updated before the deleted node is deallocated.

## Load Factor and Rehashing

The load factor measures the average number of entries per bucket.

```text
Load Factor = Number of Entries / Number of Buckets
```

The implementation provides:

```cpp
map.load_factor();
map.max_load_factor();
map.max_load_factor(0.75f);
map.bucket_count();
```

The default maximum load factor is `0.75`.

When a new insertion would exceed this threshold, the implementation increases the bucket count and redistributes the existing entries.

The manual rehash operation is:

```cpp
map.rehash(32);
```

Rehashing involves:

1. Allocating a new bucket array.
2. Calculating new bucket indices.
3. Redistributing existing entries.
4. Replacing the old bucket array.

The existing entries are relinked rather than copied into newly allocated `Entry` objects.

This can help reduce the length of linked lists and improve average lookup performance.

## Memory Management

The map owns two kinds of dynamically managed resources:

- The bucket array.
- The individual `Entry` nodes.

The constructor allocates the bucket array.

The destructor clears the entries and then releases the bucket array.

```cpp
~CustomHashMap()
{
    clear();
    delete[] buckets_;
}
```

The `clear()` operation deletes all entries and resets the bucket heads to `nullptr`. It retains the bucket array so that the map can be reused.

```cpp
map.clear();
map.insert(1, 100);
```

The implementation uses raw pointers for the persistent bucket array and linked-list nodes, making manual resource management an important part of this project.

## Rule of Five

Because `CustomHashMap` owns dynamically allocated memory, automatically generated copy operations would be unsafe: copying its raw pointers could cause two objects to own the same resources.

The implementation therefore defines the five special member functions:

1. Destructor.
2. Copy constructor.
3. Copy assignment operator.
4. Move constructor.
5. Move assignment operator.

### Copy Semantics

Copying creates an independent map with its own bucket array and entries.

Changes to the copied map should not modify the original map.

### Move Semantics

Moving transfers the owned resources from one map to another rather than copying all entries.

The moved-from object is reset to an empty internal state and is designed to support subsequent insertion.

These operations help prevent double deletion and resource ownership errors.

### Example Usage

```cpp
#include <iostream>
#include <string>
#include "custom-hashmap.hpp"

int main()
{
    CustomHashMap<int, std::string> map;

    map.insert(1, "Alice");
    map.insert(2, "Bob");

    if (const std::string* value = map.find(1))
    {
        std::cout << *value << '\n';
    }

    map[3] = "Charlie";

    std::cout << std::boolalpha;
    std::cout << map.contains(2) << '\n';
    std::cout << map.size() << '\n';

    map.erase(2);

    std::cout << map.load_factor() << '\n';

    return 0;
}
```

`operator[]` inserts a missing key with a default-constructed value. For an `int` value, that default value is `0`.

The `find()` function returns a pointer, so callers must check that the pointer is not `nullptr` before dereferencing it.

## Time Complexity

Let `n` represent the number of entries and `b` the number of buckets.

| Operation | Average Case | Worst Case |
|---|---|---|
| `insert()` | O(1) | O(n) |
| `find()` | O(1) | O(n) |
| `contains()` | O(1) | O(n) |
| `erase()` | O(1) | O(n) |
| `operator[]` | O(1) | O(n) |
| `clear()` | O(n + b) | O(n + b) |
| `size()` | O(1) | O(1) |
| `empty()` | O(1) | O(1) |
| `rehash()` | O(n + b + b')* | O(n + b + b')* |

`b'` represents the requested new bucket count. The rehash implementation also uses temporary storage proportional to the number of entries.

Average-case constant-time operations assume a reasonable hash distribution and a controlled load factor. If many keys collide into the same bucket, lookup, insertion, and deletion can degrade to linear time.

## Benchmarking

The benchmark compares `CustomHashMap<int, int>` with `std::unordered_map<int, int>` for three operations:

- Insertion.
- Successful lookup.
- Erasure.

Both implementations receive the same shuffled sequence of integer keys. The benchmark also checks a lookup checksum to verify that both maps return matching aggregate values.

The lookup benchmark constructs the maps before starting the timer, so map construction is not included in the measured lookup duration. Similarly, the erase benchmark constructs the maps before timing the deletion loop.

### Interpreting Results

The benchmark reports elapsed time in milliseconds and a custom-to-standard timing ratio.

```text
Custom / Standard = Custom Time / Standard Time
```

- A ratio near `1.0x` indicates similar measured durations.
- A ratio above `1.0x` means the custom implementation took longer in that run.
- A ratio below `1.0x` means the custom implementation took less time in that run.

These are local measurements, not universal performance guarantees. Results can vary with compiler optimization, system load, CPU behavior, and memory allocation.

For more reliable comparisons, use optimized builds and multiple repetitions. The current benchmark is a learning-oriented baseline rather than a comprehensive performance study.

## Limitations

This is an educational implementation, not a drop-in replacement for `std::unordered_map`.

Current limitations include:

- No iterator interface.
- No `at()`, `emplace()`, `try_emplace()`, or `insert_or_assign()` API.
- No thread-safety guarantees.
- No allocator customization.
- `operator[]` requires a default-constructible `Value`.
- Erasing an entry or rehashing can invalidate pointers returned by `find()`.
- Changing a stored key directly is not supported.
- Performance depends on hash quality and collision distribution.
- More extensive exception-safety, sanitizer, and stress testing is still advisable.
